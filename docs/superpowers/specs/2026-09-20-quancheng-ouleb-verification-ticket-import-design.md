# 泉城欧乐堡验证金额门票明细导入设计

## 背景

泉城欧乐堡门票对账文件 `对账明细-2026.08.28-2026.09.xlsx` 包含
`明细8.28-9.6` 和 `明细9.7-9.13` 两张工作表。该文件不是现有抖音标准明细，
但业务平台归属为抖音，金额计算基数为表内的“验证金额”。

两张工作表的列顺序不完全一致，因此解析必须按表头名称定位字段，不能使用固定列号。

## 业务口径

- 景区：泉城欧乐堡。
- 平台：抖音。
- 两张工作表全部纳入本期。
- 华林园风景区和泉城欧乐堡动物王国的有效明细全部纳入。
- 本文件所有明细状态均为“已使用”。解析时仅纳入状态为“已使用”且“验证金额”为有效数字的行。
- 核销数量取“验证总数”合计。
- 服务商到账取“验证金额”合计。
- 该格式的服务商佣金固定为 0，不从验证金额中扣减。
- 景区核销金额 = 验证金额合计 × 景区配置核销率。
- 结算金额 = 验证金额合计 × 景区配置结算费率。
- 服务费 = 结算金额 − 景区核销金额。
- 金额按整期合计计算后四舍五入到分，避免逐行或逐日舍入造成累计偏差。

## 格式识别与隔离

只有同时满足以下条件时才启用本设计：

1. 当前景区 ID 为泉城欧乐堡 `quancheng-ouleb`；
2. 工作表表头包含“订单状态”“验证总数”“验证金额”；
3. 文件中没有被现有解析器优先识别为标准抖音、美团、携程或同程格式。

识别成功后，所有符合条件的工作表聚合成一条抖音台账草稿。其他景区及泉城欧乐堡
既有标准平台文件继续沿用原解析和计算规则。

## 数据流

解析器按表头读取每行的订单状态、验证总数、验证金额、首次入园时间和完成时间：

- 使用首次入园时间作为业务日期；缺失时回退到完成时间。
- 对账周期优先使用有效明细的最早和最晚业务日期。
- 逐日快照保留验证金额，并标识为泉城验证金额格式，供上传预览、保存、编辑费率和历史重算使用。
- 计算引擎识别该标识后，以验证金额为固定基数，佣金固定为 0，并按整期计算核销金额和结算金额。

## 样例验收值

源文件应解析得到：

- 有效核销数量：`4,064`；
- 验证金额合计：`382,577.38` 元；
- 对账周期：`2026-08-28` 至 `2026-09-13`；
- 平台：抖音。

当泉城欧乐堡配置核销率为 90%、结算费率为 94% 时：

- 景区核销金额：`382,577.38 × 90% = 344,319.64` 元；
- 结算金额：`382,577.38 × 94% = 359,622.74` 元；
- 服务费：`15,303.10` 元。

实际导入必须读取景区当前配置费率，不在代码中写死 90% 或 94%。

## 异常处理

- 缺少必要表头时不把工作表识别为该格式。
- 核销率或结算费率使用现有景区配置校验范围。
- 无有效明细时返回现有“未解析到有效核销明细”提示。
- 非数字验证金额不参与汇总，避免标题、合计或空行被重复计入。

## 测试与部署

自动化测试覆盖：

- 不同列顺序的多工作表按表头解析；
- 华林园和动物王国明细全部计入；
- 平台、数量、周期和验证金额汇总；
- 90%/94% 样例金额；
- 修改费率后的重新计算；
- 其他景区和现有标准抖音格式不受影响。

测试通过后，仅打包本需求及此前已确认发布的业务文件，部署到生产服务器，检查后端健康状态，
并使用同一源文件在生产计算链路中复核验收值。
