# 门票台账到账与佣金修复及历史重算设计

日期：2026-08-11

## 目标

修复门票台账上传解析中的三个业务口径，并使用生产环境保留的原始 Excel
明细重算受影响的历史台账：

1. 同程服务商到账取明细中的「订单金额」，不再取「商家应收」。
2. 遵义动物园抖音服务商到账按费用净额计算，退款和冲正金额保留原始正负号，
   不再逐行取绝对值。
3. 福州欧乐堡抖音商品 ID `1870851250521100` 的默认服务商佣金为 0；
   其他商品继续按该台账行的佣金率计算。

修复同时覆盖后续新上传、编辑佣金率后的逐日重算和现有历史台账，且不改变福州
欧乐堡 2026/7/2-2026/7/25 的服务商到账 `1203013.49`。

## 当前问题

### 同程字段映射

当前解析器使用「商家应收」作为同程服务商到账。生产源文件同时包含「订单金额」
和「商家应收」，业务要求使用前者。三个已保存遵义动物园同程账期的原始汇总为：

| 核对日期 | 订单金额 | 商家应收（当前错误值） |
| --- | ---: | ---: |
| 2026/4/27-2026/5/24 | 8666.00 | 8146.04 |
| 2026/5/25-2026/6/21 | 1589.00 | 1493.66 |
| 2026/6/22-2026/7/26 | 1161.00 | 1091.34 |

### 遵义抖音冲正

遵义专用公式当前对每行达人服务费和服务商服务费取绝对值后扣减。退款或冲正行的
费用为正数，逐行取绝对值会将应加回的费用再次扣减。2026/4/17-2026/4/26 的
冲正费用为 `7.72`，因此系统结果少了 `15.44`。

正确口径按原始有符号列值线性累计：

`服务商到账 = 订单实收金额 + 达人服务费 + 服务商服务费`

费用正常扣收时为负数，退款或冲正时为正数。该公式等价于从订单实收中扣除费用
净额。目标账期结果为 `307337.16`。

### 福州指定商品免佣

福州欧乐堡 2026/7/2-2026/7/25 的抖音服务商到账公式和当前结果正确：

`1276334.00 - 67365.05 - 5250.42 - 705.04 = 1203013.49`

其中商品 ID `1870851250521100` 的订单实收为 `20111.00`，达人服务费和团长
服务费均为 0。该历史台账佣金率为 8%，当前该商品产生默认佣金 `1608.88`。
业务要求这部分默认佣金固定为 0。

## 方案选择

采用“解析器修复 + 可重复执行的原始文件重算工具”。不采用固定金额 SQL 更新，
因为固定更新无法修复逐日快照，也无法保证后续编辑佣金率时仍遵守新规则。不增加
后台重算按钮，避免扩大运维能力和权限面。

## 解析与计算设计

### 同程

同程平台识别仍允许通过现有同程表头确定，但解析阶段必须定位「订单金额」。缺少
该列时明确报错，不允许静默使用「商家应收」或生成空草稿。服务商到账、逐日到账
和后续计算均使用「订单金额」。

### 遵义抖音

遵义专用公式直接累加原始有符号的达人服务费和服务商服务费。删除逐行费用绝对值
归一化。逐日到账也使用同一公式，确保上传预览、保存、编辑费率和历史重算使用
同一数据快照。

### 福州指定商品免佣

规则限定为：

- 景区：`fuzhou-ouleb`
- 平台：抖音
- 商品 ID：`1870851250521100`

解析每条抖音明细时，到账仍使用全部订单。佣金基础仅累计非免佣商品的订单实收、
达人服务费和团长服务费。逐日快照新增三个紧凑字段，分别保存可计佣实收、可计佣
达人服务费和可计佣团长服务费。计算引擎优先使用这三个字段计算默认佣金；旧快照
没有新字段时回退到原有实收、达人和团长字段，保持兼容。

人工输入的佣金总额仍作为 override。佣金率变化时，只对非免佣商品的逐日基础
重算，指定商品始终不产生默认佣金。佣金总额人工调整的逐日分摊也仅按可计佣实收
分配，免佣商品不承担默认佣金。

## 历史重算

新增后端运维脚本，支持 `dry-run` 和显式 `--apply`。处理范围只包括：

- 遵义动物园全部历史抖音门票行；
- 遵义动物园全部历史同程门票行；
- 福州欧乐堡全部历史抖音门票行。

脚本按 `scenic_id + detail_stored` 对原始文件分组，每个文件只解析一次，再按平台
匹配数据库行。正式更新前完成全部文件存在性、平台匹配和解析校验；任何一项失败，
整批不写入。

每行更新以下系统计算快照：

- 服务商到账；
- 逐日明细；
- 默认服务商佣金；
- 出版应得；
- 景区核销；
- 结算金额；
- 服务费；
- 订单数和正向订单数。

人工值保护规则：

1. 若原服务商到账等于旧逐日快照到账合计，视为系统值并更新；否则视为人工到账，
   保留该值。
2. 若原佣金等于旧逐日快照按原佣金率计算的结果，视为系统默认佣金并应用免佣
   规则；否则保留人工佣金，并按人工总额重新分摊。
3. 若原核销或结算金额与旧逐日计算结果不同，视为人工覆盖并保留；服务费继续保持
   `结算金额 - 核销金额`。
4. 付款日期、付款金额、跟投金额、回款、确认函、上传人、产品名和费率快照均保留。

所有目标行更新完成后，按景区和账期重新计算滚动待核销金额。脚本重复执行应得到
相同结果。正式执行前先生成数据库备份，并输出每行更新前后差异供核对。

## 错误处理

- 同程文件缺少「订单金额」时上传解析失败，并指出缺失列。
- 福州免佣规则所需「商品ID」列缺失时上传解析失败，避免静默按全量计佣。
- 历史行缺少原始文件、文件路径越界、文件无法解析或无法匹配平台时，重算整批停止。
- `dry-run` 不提交数据库；`--apply` 在单一事务中完成，异常时回滚。
- 运维输出不打印数据库密码、订单号、券码或消费者信息，只打印台账行和金额差异。

## 测试

后端测试覆盖：

2. 同程缺少「订单金额」时明确报错。
3. 遵义抖音包含正向费用冲正时得到 `307337.16` 对应的公式行为。
4. 普通抖音景区继续使用订单实收、软件、达人和团长费用净额。
5. 福州指定商品的到账正常计入，但默认佣金贡献为 0。
6. 福州其他商品继续按佣金率计算，修改佣金率后免佣商品仍为 0。
7. 旧版逐日 JSON 缺少可计佣字段时保持原有结果。
8. 历史重算的预演、正式更新、人工值保护、缺文件回滚和幂等性。
9. 受影响的解析器、计算引擎、接口联动测试和完整后端测试均通过。

## 部署顺序

1. 部署后端解析器、计算引擎、测试和重算脚本。
2. 备份生产数据库。
3. 在生产执行历史重算 `dry-run`，核对目标行差异。
4. 执行正式重算并再次查询验收金额。
5. 重启后端，使用三类代表性文件验证新上传预览。

本次无前端交互和数据库表结构变更。
