# 泉城欧乐堡酒店品牌与平台拆分导入设计

## 背景

泉城欧乐堡酒店核销文件 `海洋骑士长颈鹿2026.1.25-2.21.xlsx` 含 18 个工作表，分别覆盖海洋、骑士、长颈鹿三个酒店品牌及携程、美团两个平台。现有解析器只按基础平台聚合，上传后会把三个酒店品牌合并成“携程”“美团”两行，无法满足一期展示六行以及逐品牌核对的要求。

## 目标

- 同一上传文件按“酒店品牌 × 基础平台”聚合为一期六行。
- `hotel_name` 保存 `海洋`、`骑士`、`长颈鹿`，`platform` 保持标准值 `携程`、`美团`。
- 页面以组合标签展示 `海洋携程`、`海洋美团`、`骑士携程`、`骑士美团`、`长颈鹿携程`、`长颈鹿美团`。
- 六行分别保存独立逐日快照，沿用现有逐日四舍五入计算规则。
- 未包含受支持酒店品牌的旧文件仍按原有平台维度聚合，保持向后兼容。

## 解析设计

解析器从工作表名称中分别识别：

- 基础平台：沿用 `抖音`、`美团`、`携程` 的现有识别规则。
- 酒店品牌：识别工作表名称开头的 `海洋`、`骑士`、`长颈鹿`。

聚合键由单一 `platform` 改为 `(hotel_name, platform)`。未识别到酒店品牌时，`hotel_name` 为空并继续按基础平台聚合，保证普通文件输出与现状一致。

每个聚合组独立维护：

- 结算基数、间夜、订单数、正向订单数；
- 日期跨度；
- 按日期归集的计算快照 `daily_json`。

响应模型新增可选 `hotel_name`。品牌文件按酒店品牌顺序输出，每个品牌内按携程、美团输出；普通文件继续沿用原有平台顺序。

## 前端设计

- 草稿行优先采用解析响应中的 `hotel_name`，仅在未返回品牌时使用现有默认酒店名称。
- 草稿和已保存台账的平台标签使用 `hotel_name + platform`；合计行仍显示“本期合计”“总合计”。
- 已保存行按酒店品牌和基础平台稳定排序，确保一期六行顺序为海洋携程、海洋美团、骑士携程、骑士美团、长颈鹿携程、长颈鹿美团。
- 保存请求仍分别提交 `hotel_name` 与 `platform`，不把组合名称写入平台字段。

## 测试范围

- 后端解析器测试：品牌识别、六组拆分、顺序、逐组金额和逐日计算结果。
- 后端兼容测试：无品牌工作表仍按平台合并且不强制酒店名称。
- 接口响应测试：`hotel_name` 正确进入解析草稿模型。
- 前端工具测试：解析品牌优先于默认酒店名称，保存时维持品牌与平台分字段。
- 前端展示测试：组合标签与品牌优先排序。
- 使用用户提供的真实文件执行只读验收，逐项核对上述六行。

## 非目标

- 不改变泉城欧乐堡费率、服务费算法或期次滚动逻辑。
- 不按订单号去重，不改变取消及冲销数据的现有计算口径。
- 不迁移或重写历史酒店台账。
