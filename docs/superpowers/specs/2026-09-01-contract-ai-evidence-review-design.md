# 合同 AI 证据审查设计

## 目标

将现有“合同全文 + 知识库前 8000 字 + DeepSeek 自由 Markdown”改造成可验证的证据审查链路。审查既保留对我方不利条款识别，也必须核验合同中的关键事实和法律主张，并展示每项判断实际引用的知识库证据。

成功标准：

- 知识库不再按文档顺序截取，而是按合同内容召回相关片段。
- 合同中的错误法律说法、金额/日期/比例冲突和关键主体不一致能够被显式列出。
- 每个知识库判断都绑定文档标题、片段编号和原文摘录。
- 无证据时必须返回“知识库未找到依据”，不能用模型既有认知冒充知识库结论。
- DeepSeek 不可用时，确定性核验仍然运行，且前端明确展示降级原因。

## 范围

本次只改造合同管理中的“AI 合同审查”。审批单合同校对、客户尽调、经营诊断和通用 AI 助手保持现状。

不新增向量数据库、不调用新的第三方搜索或嵌入服务、不修改 `biz_knowledge_doc` 表。现有知识库上传、下载和删除接口保持兼容。

## 架构

### 1. 文档分段

知识库全文在审查请求内按标题和段落即时分段。优先识别“第X条”“第X章”“一、”“（一）”等结构；普通长段按句子边界切分。每个片段包含：

- `chunk_id`：`<doc_id>:<ordinal>`；
- `doc_id`、`title`、`category`；
- `section`：就近识别的章节或条款标题；
- `text`：受长度限制的原文；
- `ordinal`：文档内顺序。

片段只在内存中生成，不持久化，避免引入迁移和知识库重建步骤。

### 2. 本地检索

检索输入由合同标题、合同类型、标的、付款条件、备注及附件提取正文组成。服务端从输入中提取中文词组、法条引用、百分比、金额、日期、期限和风险主题词，对知识片段评分。

评分由以下确定性信号组成：

- 完整法条或制度名称匹配；
- 关键词交集；
- 风险主题命中，例如付款、违约、管辖、招标、投资权限、担保、赔偿、解除；
- 数字、比例和期限邻近匹配；
- 标题和章节命中加权。

按文档去重后返回最多 12 个片段、总计不超过 12000 字。低于最小相关度的片段不返回。返回的 `retrieved_sources` 就是实际送入 DeepSeek 的证据，而不是整个知识库标题列表。

### 3. 确定性事实核验

在调用模型前执行无需 AI 的核验，至少覆盖：

- 同一合同内金额、日期、期限、比例的明显冲突；
- 百分比小于 0 或大于 100；
- 合同结构化字段与附件正文中的合同编号、客户名称、金额明显不一致；
- 明确引用的法规或制度名称在知识库中不存在；
- 明确法条引用在已召回证据中找不到对应条款。

确定性发现统一转换成 `fact_checks`，不能被 DeepSeek 输出覆盖或删除。

### 4. DeepSeek 结构化审查

模型只收到：合同文本、结构化合同字段、检索证据和确定性发现。模型必须输出 JSON，而不是自由 Markdown。

每个事实核验项包含：

- `claim`：合同原始说法；
- `verdict`：`supported`、`contradicted`、`not_found`、`not_applicable`；
- `reason`：简明原因；
- `contract_quote`：合同定位或原文；
- `evidence_ids`：只能引用给定 `chunk_id`；
- `risk_level`：`high`、`medium`、`low`；
- `suggestion`：可直接落地的修改建议。

风险条款项沿用条款定位、风险和建议三要素，同时增加 `evidence_ids`。模型被禁止根据训练记忆补写知识库没有的法条；找不到证据时必须使用 `not_found`。

### 5. 服务端证据校验

模型返回后，服务端执行：

- JSON 模式和枚举校验；
- 丢弃不存在的 `evidence_ids`；
- 将证据原文从服务端检索结果回填，禁止模型自造引文；
- 知识库判断引用为空时降为 `not_found`；
- 合并并去重确定性发现；
- 根据高/中/低项计算总体风险和证据覆盖率。

覆盖率定义为：需要知识库依据的核验项中，具有至少一个有效证据片段的比例。没有可核验项时为 `0`，并显示“本次未识别到可核验法律主张”。

## 接口

`POST /api/v1/contracts/{contract_id}/ai-review` 保持路径不变，返回：

```json
{
  "markdown": "兼容复制与历史展示的完整审查文本",
  "engine": "deepseek|rule",
  "has_attachment": true,
  "fallback_reason": null,
  "fact_checks": [],
  "risk_findings": [],
  "retrieved_sources": [],
  "coverage": {
    "claim_count": 3,
    "supported_count": 2,
    "contradicted_count": 1,
    "not_found_count": 0,
    "evidence_rate": 0.67
  },
  "kb_used": ["兼容字段，仅包含 retrieved_sources 中去重后的标题"]
}
```

`markdown` 由服务端根据结构化结果生成，避免模型自由输出与结构化结果不一致。

## 前端展示

现有合同审查弹窗保留，新增：

- 顶部状态：DeepSeek/规则引擎、附件来源、检索证据篇数、证据覆盖率；
- “事实与法规核验”表格：主张、结论、风险等级、原因、建议；
- 每项下方可展开“法规依据”，展示法规标题、章节和原文摘录；
- “风险条款”继续使用 Markdown 展示；
- 降级时显示 `fallback_reason`，禁止把规则结果标成已由知识库核实；
- `not_found` 使用黄色状态，文案为“知识库未找到依据”；`contradicted` 使用红色状态。

## 错误处理

- 合同附件无法提取时继续使用结构化字段，但响应明确 `has_attachment=false`。
- 知识库为空或检索不到相关片段时仍执行确定性核验，所有需要知识库的主张标记为 `not_found`。
- DeepSeek 超时、限流、JSON 无效或返回空内容时，`engine=rule`，保留确定性核验并返回非敏感 `fallback_reason`。
- 任何模型输出都不能删除确定性错误，也不能引用未检索的知识片段。
- 接口继续保持业务约定，不因大模型故障返回 500。

## 测试

后端增加以下回归覆盖：

- 17 份文档中相关内容位于后续文档时仍能召回，证明不再只取第一份前 8000 字；
- 错误法条、错误比例、结构化金额与附件金额不一致被识别；
- 正确说法标记为 `supported` 并返回真实证据；
- 找不到依据时标记为 `not_found`；
- 模型引用不存在的 `chunk_id` 会被丢弃并降级结论；
- DeepSeek 失败时确定性发现和 `fallback_reason` 仍返回；
- 接口兼容 `markdown`、`engine`、`has_attachment`、`kb_used`；
- 前端正确显示矛盾、未找到依据、证据展开和降级原因。

## 安全与隐私

- 只向 DeepSeek 发送当前合同文本和本次召回的知识片段，不再发送无关知识库全文。
- 日志不记录合同正文、知识库正文或模型完整请求，只记录数量、耗时、引擎和失败类型。
- 前端只展示当前用户已有合同查看权限范围内的审查结果。
