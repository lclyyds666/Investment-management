# 鹳雀楼门票核销台账解析与计算修复设计

日期：2026-09-13

## 目标

修复鹳雀楼上传门票对账文件时的解析和核销计算问题，使用户可以直接上传
`鹳雀楼7.31-8.23.xlsx` 这类包含多景区、多平台工作表的文件，并得到只属于鹳雀楼的
门票台账草稿。修复不改变上传接口、数据库结构、前端交互和其他景区既有口径。

## 现状与问题

目标文件包含抖音、美团、携程、同程共 10 个工作表，抖音、美团、携程工作表同时含有
普救寺和鹳雀楼数据。

1. 抖音实际表头为“订单实收”，当前平台识别器只识别“订单实收金额”，导致抖音工作表
   被跳过。
2. 解析器没有按 `scenic_id` 过滤明细，已识别的平台会把普救寺金额计入鹳雀楼。
3. 鹳雀楼抖音明细中的软件、达人、撮合经纪服务费为正数，当前按负数费用相加，会高估
   服务商到账和后续结算金额。
4. 鹳雀楼抖音使用“撮合经纪服务费”字段，当前仅支持“团长服务费”，导致佣金逐日重算
   少用一个费用项。

## 方案

### 1. 平台表头兼容

在现有 `ticket_ledger` 服务中增加按别名定位列的辅助逻辑：

- 抖音订单实收列接受“订单实收”和历史名称“订单实收金额”。
- 团长费用列接受“团长服务费”和“撮合经纪服务费”，同一表优先使用明确存在的历史
  名称，缺失时使用兼容名称。
- 抖音平台识别使用“核销时间”加上述任一订单实收列，不再依赖单一固定名称。

### 2. 鹳雀楼明细筛选

增加景区匹配器，仅对已知 `scenic_id` 配置筛选规则；未配置的景区沿用原逻辑，避免
改变历史结果。`guanquelou` 的匹配关键字为“鹳雀楼”，平台字段如下：

| 平台 | 筛选字段 | 匹配方式 |
| --- | --- | --- |
| 抖音 | 核销门店 | 文本包含“鹳雀楼” |
| 美团 | 产品名称 | 文本包含“鹳雀楼” |
| 携程 | 资源名称 | 文本包含“鹳雀楼” |
| 同程 | 景区名称 | 等于“鹳雀楼” |

目标景区缺少对应筛选列时抛出明确的解析错误，不生成可能跨景区的草稿。筛选发生在
平台金额、票数、正向票数、日期和逐日快照累加之前。

### 3. 鹳雀楼抖音费用口径

鹳雀楼抖音明细按费用符号判断口径，并保留原始正负号语义：

- 新式正数费用：服务商到账 = 订单实收 − 软件服务费 − 达人服务费 − 撮合经纪服务费。
- 旧式负数费用：继续使用现有有符号相加规则。
- 若“服务商服务费”列存在且为正数，将其作为服务商到账的权威净额；组成项用于
  校验，不能用该列与组成项重复累加。

佣金仍按订单实收乘佣金率再扣除达人和团长/撮合经纪费用。为了让保存后的编辑行为与
上传预览一致，解析时将佣金输入按当前费用符号归一化写入逐日快照 `cs/cd/ct`；
后续 `recompute_from_json` 直接使用归一化字段，旧快照没有这些字段时保持现有回退逻辑。

核销金额、结算金额和服务费继续由逐日到账按景区核销率、结算费率逐日四舍五入后累加，
不修改 `ledger_calculator` 的通用舍入规则或期次滚动待核销规则。

## 数据流

1. 上传接口按原流程读取文件、读取景区配置并调用 `parse_reconciliation`。
2. 解析器扫描工作表，使用兼容表头识别平台。
3. 对鹳雀楼按平台筛选字段过滤明细，按日期聚合到账、票数和佣金输入。
4. 计算服务商佣金、出版应得、景区核销、结算和服务费，生成带归一化逐日快照的草稿。
5. 保存、编辑、费率调整和历史逐日恢复继续调用现有计算入口，不需要数据库迁移或前端
   协议变化。

## 错误处理与兼容性

- 目标景区缺少筛选字段时明确报告缺失列。
- 文件未找到鹳雀楼明细时沿用现有“未解析到有效核销明细”提示，不伪造金额。
- 其他景区不启用新筛选器；旧抖音表头、旧负数费用和旧逐日 JSON 均保持兼容。
- 不改变同程使用“订单金额”、携程仅计入“订单成本”、美团仅计入“消费结算”的既有
  平台规则。

## 测试与基准

新增后端单元测试，不将 12MB 生产文件提交到仓库。测试覆盖：

1. 混合景区四平台文件只保留鹳雀楼行，并正确统计票数与日期。
2. 抖音“订单实收”新表头、“订单实收金额”旧表头均可识别。
3. “撮合经纪服务费”兼容字段参与到账和佣金计算，正负费用口径正确。
4. 缺少鹳雀楼筛选字段时解析失败并指出字段名称。
5. 归一化逐日 JSON 在修改佣金率后得到与上传计算一致的结果。
6. 现有门票解析、携程/同程规则和通用计算器测试继续通过。

## 非目标

- 不生成或修改用户桌面的 Excel 结果文件。
- 不新增手工重算按钮、数据库字段、迁移或前端展示字段。
- 不调整其他景区的历史数据和结算算法。
